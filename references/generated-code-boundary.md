# 生成物边界

哪些文件由生成器拥有、哪些由项目维护、允许的例外怎么登记。

## 所有权表

| 路径 | 归属 | 变更方式 |
|---|---|---|
| `rpc_gen/kitex_gen/**` | Kitex 生成器 | 只能重新生成 |
| `rpc_gen/rpc/{svc}/*` | cwgo client 模板生成 | 只能重新生成 |
| `app/{svc}/handler.go` | Kitex / cwgo 生成 | 只能重新生成 |
| `app/{gw}/hertz_gen/**` | hz 生成 | 只能重新生成 |
| `app/{gw}/biz/router/**` | hz 生成 | 只能重新生成；`middleware.go` 的方法体是用户扩展点 |
| `app/{gw}/biz/handler/{pkg}/*_service.go` | hz / cwgo 生成（见下方两个例外） | 重新生成 |
| `app/{gw}/biz/handler/{pkg}/*_service_test.go` | cwgo 生成的 `ut` 桩 | 保留，可不填充 |
| `app/{gw}/.hz` | hz 生成的项目标记 | 提交进仓库，不要手改 |
| `app/{svc}/biz/service/{method}.go` | 项目维护（手写） | 直接编辑 |
| `app/{svc}/biz/service/init.go` | 项目维护 | 直接编辑 |
| `app/{svc}/biz/{dao,model,pack,producer,dal}` | 项目维护 | 直接编辑 |
| `app/{svc}/infra/rpc/client.go` | 项目维护 | 直接编辑 |
| `hcommon/pkg/responsex` | 项目维护（网关公共库） | 直接编辑；两个网关共用 |
| `app/{svc}/main.go`、`build*.sh`、`conf/` | 生成一次后项目维护（`main.go` 带 `Code generated` 头但模板是 `skip`） | 直接编辑 |
| `app/{gw}/main.go`、`router.go`、`router_gen.go`、`conf/` | hz 生成一次后项目维护（`skip`） | 直接编辑 |
| `app/{gw}/biz/handler/{pkg}/sse.go` | 项目维护（流式桥接） | 直接编辑 |

判断不准时看文件头：有 `Code generated by ... DO NOT EDIT.` 的是生成物。`{method}.go`、`responsex`、`middleware.go` 的方法体由项目维护。

形态 A（cwgo）首次生成会多出 `biz/utils/resp.go` 桩和 `conf/`、`biz/dal/`、`build.sh`、`docker-compose.yaml`、`readme.md`。`resp.go` 桩只有 `c.JSON(code, data)` / `c.String(code, err.Error())`，没有信封，要替换成 `responsex`；其余脚手架直接删。

## 为什么不能手改生成物

生成物的内容完全由 IDL 和生成器版本决定。手改的内容会在下一次 `make gen-*` 时被覆盖或产生不一致的 diff，而且无法通过 review 判断"哪些是故意的"。生成后 `git diff` 里出现预期外的改动，是版本或参数漂移的最早信号。

## 例外一：新方法 handler 改成委托形状

### 问题

`hz update` 给已有 handler 文件**追加**新方法时，用的是 hz 原生模板，不委托 service：

```go
func ProbeSkill(ctx context.Context, c *app.RequestContext) {
    var err error
    var req user.ProbeSkillReq
    err = c.BindAndValidate(&req)
    if err != nil {
        c.String(consts.StatusBadRequest, err.Error()) // 错误文案直接透给客户端
        return
    }
    resp := new(user.ProbeSkillResp)
    c.JSON(consts.StatusOK, resp)                      // 没有信封，空响应
}
```

这会让一个端点与其他端点的响应形状不一致，并把绑定错误的内部文案透给前端。所以新方法追加后，要把它的 handler 体改成三分支委托形状，并手写对应的 `biz/service/{method}.go`。

### hz 的更新语义

`hz update` 对已存在的 handler 文件按**方法名增量合并**：只追加 IDL 里新增的方法，已存在的方法体原样保留。实测（hz v0.9.7）：

| 操作 | 已有方法体 | 新增方法 |
|---|---|---|
| `hz update` 追加 | 逐字节保留 | hz 原生形状 |
| `cwgo server --type HTTP` 重生成 | 逐字节保留（含手改的绑定分支和标记注释） | cwgo 模板形状 |
| IDL 删除某方法后再 update | 被删方法成为孤儿，不自动清理 | — |

在 [fixtures/stream-sse](../fixtures/stream-sse) 上可以直接复现：对已带桥接的网关再跑一次 `cwgo server --type HTTP`，`echo_service.go` 逐字节不变，`sse.go` 与标记都保留。

会丢失的情况只有两种：`hz new --force`，或删掉整个 handler 文件后重建。这两种操作之后必须按下方清单逐个恢复手改。

### 目标形状

```go
func ProbeSkill(ctx context.Context, c *app.RequestContext) {
    var req user.ProbeSkillReq
    if err := c.BindAndValidate(&req); err != nil {
        responsex.SendBindErrorResponse(ctx, c, err)
        return
    }
    resp, err := service.NewProbeSkillService(ctx, c).Run(&req)
    if err != nil {
        responsex.SendErrResponse(ctx, c, consts.StatusBadRequest, err)
        return
    }
    responsex.SendSuccessResponse(ctx, c, consts.StatusOK, resp)
}
```

三个分支各用哪个响应函数是固定的：绑定失败 → `SendBindErrorResponse`，业务失败 → `SendErrResponse`，成功 → `SendSuccessResponse`。第三个参数（状态码）被信封函数忽略，保留生成器给的值即可。

### 登记约定

1. 只改新方法自己的 handler 体，不动同文件里其他方法。
2. 在同一个提交里手写 `biz/service/{method}.go`，形状见 [hertz-gateway.md](hertz-gateway.md)。
3. 在仓库的生成命令附近（Makefile 注释或 `docs/`）登记一句：新方法 handler 已改成委托形状。

### 生成后检查

```bash
# 不应有任何方法还是 hz 原生形状（两条都应无输出）
grep -n 'c.String(consts.StatusBadRequest' app/apigw/biz/handler/*/*_service.go
grep -n 'c.JSON(consts.StatusOK' app/apigw/biz/handler/*/*_service.go
```

两条都应无输出；有输出就是漏改的新方法（流式桥接的方法除外，它们调用的是桥接函数）。主参考库的 `make gen-gw` 用一行 perl 在生成后自动完成绑定分支的改写；本 skill 不依赖 perl，生成后按上面的形状手改一次即可，之后 `hz update` 不会再碰它。

> 主参考库 Makefile 里那条 perl 正则匹配的是 `utils.SendErrResponse`，handler 迁到 `responsex.` 之后它已经**匹配不到任何东西**。生成后不要假设绑定分支已被自动改写，按上面两条 `grep` 核对。

## 例外二：流式 handler 桥接

### 问题

普通 handler 委托 service 后用统一函数回 JSON。流式端点不能这样收尾：它需要拿到 Kitex 的 stream 对象后持续写 SSE。所以 handler 函数体必须改成调用一个桥接函数，而 handler 文件本身是生成物。

### 登记约定

1. 桥接逻辑写在同包的独立文件 `sse.go`（或 `{method}.go`），**不**写在生成的 `*_service.go` 里。
2. handler 里的改动只有一处：把 `resp, err := service...Run(&req)` 之后的 JSON 收尾替换成 `writeSSEStream(c, stream)`。
3. 桥接函数上方加标记注释，供检查脚本识别：

```go
// cloudwego-skills: sse-bridge <MethodName> — registered exception, see references/generated-code-boundary.md
func writeSSEStream(c *app.RequestContext, stream orderservice.OrderService_WatchStreamClient) {
```

4. 在仓库的生成命令附近（Makefile 注释或 `docs/`）登记一行：方法名、文件、恢复步骤。

> 主参考库现有的桥接函数（`app/apigw/biz/handler/dialogue/sse.go` 的 `writeSSEStream`）**尚未加**这个标记注释。SSE 协议仍在调整，本 skill 暂不要求补标；等协议定稿后一并处理。

### 重新生成后检查

```bash
# 每个流式方法都应命中：handler 调用桥接，且 sse.go 带标记
grep -n 'writeSSEStream' app/apigw/biz/handler/<pkg>/<pkg>_service.go
grep -n 'cloudwego-skills: sse-bridge' app/apigw/biz/handler/<pkg>/sse.go
```

任一缺失即说明桥接丢失，按 [workflows/add-streaming-endpoint.md](../workflows/add-streaming-endpoint.md) 的"恢复桥接"步骤恢复后再继续。

> SSE 协议仍在调整，这一节只描述登记机制。

## 孤儿 handler

增量合并的另一面：IDL 里**改名或删除**方法后，旧 handler 函数不会被自动清理，会留在文件里成为孤儿。它仍能编译，但不再被任何路由引用。处理方式：

- 在 IDL 改动同一个提交里，手动删掉生成的 handler 中对应的孤儿函数与孤儿 import；
- 这类删除是允许的：删除生成物里的函数是让它与 IDL 对齐，不是注入业务逻辑。

## 不属于例外的情形

- 想在普通 handler 里加日志、改状态码、换响应格式 → 改 `responsex` 或 service。
- 想给某个路由加中间件 → 改 `biz/router/{pkg}/middleware.go` 里对应的 `_{method}Mw()`，这个文件是生成器留给用户的扩展点。
- 想加非 IDL 定义的路由（如第三方支付回调）→ 写在根目录 `router.go` 的 `customizedRegister`，这是 hz 预留的手写入口。
- 想复用存量代码那种"`Run` 里自己调 `validateRequestSession`"的写法 → 那是未迁移完的遗留，新端点用中间件。

## 存量遗留：对话域的网关 service 仍自行校验令牌

主参考库 `apigw` 的对话域（`chat`、`chat_stream`、`list_conversation`、`list_message`、`mark_conversation_read`、`get_chat_setting`、`update_chat_setting`）对应的路由中间件仍是 `return nil` 桩，service 在 `Run` 里自己调 `support.go` 的 `validateRequestSession`。这是未迁移完的遗留：

- **新端点**一律按"中间件挂 `mw.MustLoginMw()` + `mw.UserID`"写，不要复制 `validateRequestSession`。
- 改到这批遗留端点时，不要顺手迁移——它们的 service 从 `session` 里还取了别的字段，迁移要单独评估。
